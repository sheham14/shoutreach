SSH & Linux Reference

General guide · Written during ShoutReach GCP deployment · May 2026

A practical reference for working on a remote Linux server. Commands are written for Debian/Ubuntu — they work the same on most Linux distros.

SSH Basics

SSH (Secure Shell) lets you control a remote server from your terminal as if you were sitting at it.

Connecting

# Basic connection
ssh username@server-ip

# Example
ssh sheham_shahid@34.123.45.67

# Connect on a non-default port (default is 22)
ssh -p 2222 username@server-ip

# Connect with a specific key file
ssh -i ~/.ssh/my_key username@server-ip

Disconnecting

# Clean exit
exit

# Force close if frozen
# Press: ~ then . (tilde, then period)
GCP tip: You can also connect directly in the browser via the SSH button in Compute Engine — no local setup needed.

SSH Keys

Keys are more secure than passwords. A key pair has two parts: a private key (stays on your machine) and a public key (goes on the server).

Generate a key pair

# Generate an Ed25519 key (modern, recommended)
ssh-keygen -t ed25519 -C "your-label" -f ~/.ssh/my_key

# -C adds a comment/label to identify the key
# -f sets the filename (default is ~/.ssh/id_ed25519)

Add public key to a server

# The easy way — copies your key to the server
ssh-copy-id -i ~/.ssh/my_key.pub username@server-ip

# Manual way — paste the public key into authorized_keys
cat ~/.ssh/my_key.pub   # copy this output
# Then on the server:
echo "PASTE_PUBLIC_KEY_HERE" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

View your public key

cat ~/.ssh/my_key.pub

Permissions

Linux controls who can read, write, or execute each file.

# View permissions
ls -la

# Output looks like:
# -rw-r--r-- 1 sheham_shahid sheham_shahid 1234 May 17 file.txt
# ^ rwx bits   ^ owner          ^ group

# Change permissions (numbers: 4=read, 2=write, 1=execute)
chmod 600 file.txt     # owner read+write only (good for keys/secrets)
chmod 644 file.txt     # owner rw, others read-only
chmod 755 script.sh    # owner rwx, others rx (executable script)

# Change owner
sudo chown username:username file.txt

systemd Services

systemd manages long-running background processes (services). It starts them on boot, restarts them on crash, and lets you check their status.

Common commands

CommandWhat it does
sudo systemctl start nameStart a service
sudo systemctl stop nameStop a service
sudo systemctl restart nameStop and start (picks up code/config changes)
sudo systemctl reload nameReload config without full restart (nginx)
sudo systemctl enable nameStart automatically on boot
sudo systemctl disable nameDon't start on boot
sudo systemctl status nameCheck if running, recent log lines
sudo systemctl daemon-reloadRe-read service files after editing them

Writing a service file

Service files live in /etc/systemd/system/

[Unit]
Description=My App
After=network.target        # wait for network before starting

[Service]
User=myuser                 # run as this user (not root)
WorkingDirectory=/home/myuser/myapp
Environment="PATH=/home/myuser/myapp/venv/bin"
EnvironmentFile=/home/myuser/myapp/.env   # load .env vars
ExecStart=/home/myuser/myapp/venv/bin/gunicorn --workers 1 --bind 127.0.0.1:8000 app:app
Restart=always              # restart if it crashes

[Install]
WantedBy=multi-user.target  # start in normal boot mode
After editing a service file, always run sudo systemctl daemon-reload before restarting — otherwise systemd uses the old version.

Logs

systemd captures all stdout/stderr from your service automatically.

# View logs for a service
sudo journalctl -u servicename

# View last 50 lines
sudo journalctl -u servicename -n 50

# Follow live (like tail -f)
sudo journalctl -u servicename -f

# View logs since a time
sudo journalctl -u servicename --since "2026-05-17 19:00"

# View nginx access log
sudo tail -f /var/log/nginx/access.log

# View nginx error log
sudo tail -f /var/log/nginx/error.log

nginx

nginx is a reverse proxy — it receives incoming HTTP requests on port 80 and forwards them to your app running on a local port (e.g. 8000).

Config files

PathPurpose
/etc/nginx/nginx.confMain config (rarely edited)
/etc/nginx/sites-available/All your site configs (inactive until linked)
/etc/nginx/sites-enabled/Symlinks to active configs

Activate a site config

# Create symlink to enable the site
sudo ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/

# Remove the default placeholder
sudo rm /etc/nginx/sites-enabled/default

# Test config for syntax errors
sudo nginx -t

# Apply changes
sudo systemctl reload nginx

Basic site config

server {
    listen 80;
    server_name _;              # _ = match any hostname
    client_max_body_size 20M;   # increase for file uploads

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

gunicorn

gunicorn is a production-grade Python web server. It runs your Flask app and handles concurrent requests.

# Basic run (for testing — use systemd in production)
gunicorn --workers 1 --bind 0.0.0.0:8000 app:app
#                ^ workers   ^ address     ^ module:flask_app_variable

# With a virtualenv
/home/user/myapp/venv/bin/gunicorn --workers 1 --bind 127.0.0.1:8000 app:app
Workers and background threads: If your app runs background threads (like APScheduler), use --workers 1. Multiple workers spawn multiple processes, each with their own scheduler thread — causing duplicate work.

Git on Server

# Clone a repo into the current directory
git clone https://github.com/user/repo.git .

# Clone a private repo with a token
git clone https://TOKEN@github.com/user/repo.git .

# Pull latest changes
git pull origin main

# Check what branch you're on
git branch

# Check status
git status

# Set up credential storage (saves token so you don't retype it)
git config credential.helper store
git pull origin main   # enter credentials once, saved after
After pulling code changes, always restart your service: sudo systemctl restart myapp

Python & Virtual Environments

A virtualenv isolates your project's Python packages from the system Python.

# Create a virtualenv
python3 -m venv venv

# Activate it (your prompt changes to show "(venv)")
source venv/bin/activate

# Deactivate
deactivate

# Install dependencies
pip install -r requirements.txt

# Install a single package
pip install flask

# See what's installed
pip list

# Run a Python script inside the venv
venv/bin/python3 script.py
In systemd service files, set Environment="PATH=/path/to/venv/bin" instead of activating — the service runs without a shell session.

Common Issues & Fixes

App not loading in browser

  1. Check the app is running: sudo systemctl status myapp
  2. Check it responds locally: curl http://127.0.0.1:8000
  3. If local works, check nginx: sudo systemctl status nginx
  4. If nginx is fine, check cloud firewall rules (port 80 must be open)

Service won't start

# See the error
sudo journalctl -u myapp -n 30

# Common causes:
# - Wrong file path in ExecStart
# - Python import error (missing package)
# - Port already in use
# - Permission denied on a file

Changes not showing after git pull

# Always restart after pulling
sudo systemctl restart myapp

# If you changed nginx config too
sudo systemctl reload nginx

Disk full

# Check usage
df -h

# Find large files
du -sh /* 2>/dev/null | sort -hr | head -20

# Clear old journal logs
sudo journalctl --vacuum-time=7d

Out of memory / server freezing

# Check memory usage
free -h

# Check swap is active
swapon --show

# Add swap if none (2GB example)
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

Permission denied errors

# Check who owns the file
ls -la filename

# Fix ownership
sudo chown yourusername:yourusername filename

# Fix permissions
chmod 644 filename    # regular file
chmod 755 filename    # executable / folder
